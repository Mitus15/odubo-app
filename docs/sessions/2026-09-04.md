which is how `gid://shopify/Product/…` ended up in page metadata.

## Domain: moved to odubostudio.com

`odubostudio.com` (registered via Vercel) is **live and correct** — NS delegated to
Vercel, apex 308→www, www 200 with valid TLS, app serving. Nothing to wait on; it is
not a propagation issue.

`odubo.studio` is the dead one: registry says ACTIVE but it has **no NS delegation at
all**, so it and every subdomain resolve for nobody, and it has no MX.

Two live bugs fixed as a result: `hostname.includes('odubo.studio')` is **false** on
`odubostudio.com` (different string — no dot), so production detection failed on the
real production domain in both `middleware.ts` and `HomePageClient.tsx`. Both now
resolve the apex from the incoming host instead of hardcoding it. `sitemap.ts` and
`robots.ts` fallbacks repointed at `https://www.odubostudio.com`.

**Customer accounts are broken end to end:** `odubostudio.myshopify.com/account` 302s
to `https://account.odubo.studio/` — dead. Customers reach that from Shopify's own
order-confirmation emails, so it breaks the post-purchase path.

# 2026-09-05 — Commerce data extraction into D1

Goal: Shopify data in the owner's own database for accounting, finance, inventory,
CRM and product intel — answerable without opening Shopify reports.

## What already existed (so nothing was rebuilt)

The warehouse was already there and already migrated to production D1 — and empty:
`commerce_orders`, `commerce_order_items`, `commerce_customers`,
`commerce_daily_metrics`, `commerce_product_metrics`, `commerce_sync_status`, plus a
BI suite (`bi_expenses`, `bi_product_costs`, `bi_ad_campaigns`, `bi_ad_metrics`,
`bi_reports`, `bi_website_metrics`, `bi_social_snapshots`).

`/api/intel/commerce` already reads **D1, not Shopify**, and `FinanceTab` already
consumes it alongside `/api/bi/product-costs` and `/api/bi/expenses/summary`. So the
"without going through Shopify reports" requirement was already architecturally met.
The gap was never the dashboard — it was that **nothing ever filled the tables**:
`/api/cron/sync-shopify` existed but was not in `vercel.json`, and the only registered
webhook was the Loop pass one.

## Done

- **COGS extracted.** 115 of 116 variants carry `inventoryItem.unitCost` in Shopify.
  Loaded into `bi_product_costs` keyed by `variant_sku`. Margins now computable today,
  with no orders needed — they range 42.3% (Jeans N°1, $40.36 on $70) to 64.4%
  (hoodies, $24.94 on $70). `commerce_order_items.sku` joins straight to
  `bi_product_costs.variant_sku`, so true per-order gross margin needs no schema change.
- **Sync scheduled** — `/api/cron/sync-shopify` added to `vercel.json` at 05:00 daily.
- **Order webhooks registered** → `https://www.odubostudio.com/api/webhooks/shopify`
  for `ORDERS_CREATE`, `ORDERS_UPDATED`, `ORDERS_CANCELLED`, `REFUNDS_CREATE`.

## Two holes closed on the way

- `/api/cron/sync-shopify` had **no auth at all**. It calls the Shopify Admin API and
  writes D1, so anyone could burn the store's rate limit and churn the commerce tables.
  Now accepts Vercel Cron's `Bearer $CRON_SECRET` or an admin session, and fails closed.
- `/api/webhooks/shopify` **skipped verification entirely** when no secret was set — and
  `SHOPIFY_WEBHOOK_SECRET` is not set. Since these payloads become the rows the finance
  dashboard reports on, that let anyone POST invented revenue into the books. Now
  verifies against `SHOPIFY_WEBHOOK_SECRET` or `SHOPIFY_ADMIN_API_SECRET` (API-registered
  webhooks are signed with the app secret, which is set) and refuses unverified payloads
  in production.

## Limits worth knowing

- **CRM is blocked at the API.** `customers` returns `ACCESS_DENIED — read_customers
  required`. Owner's call: stay PII-free, so `commerce_customers` keeps hashed ids.
  Behaviour, cohorts and LTV still work; name/email lookup stays in Shopify.
- **Inventory intel is not available from Shopify.** Every variant is `tracked: false`
  with a sentinel quantity of 9999999 — print-on-demand holds no stock here. Real
  inventory would have to come from the POD supplier.
- Shopify has **0 orders ever**, so there is nothing to backfill. The pipeline matters
  from the first sale onward.
- Not yet deployed: until this ships, production still runs the unverified webhook path.
